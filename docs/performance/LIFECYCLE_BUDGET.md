# 生命周期预算与优化账本

> 定位：本文回答一个问题——**当一个平台同时要做启动优化、稳态优化、
> 故障隔离、内存回收和生态迁移时，它们凭什么不互相打架。**
>
> 本文不是验收手册。判据、采样链路、护栏清单见
> [`STABILITY.md`](STABILITY.md)；当前实现状态见
> [`../architecture/CURRENT.md`](../architecture/CURRENT.md)。
> 与那两份文档冲突时，以它们为准。

---

## 0. 结论先行

"全选"在**目标层**成立，在**执行层**不成立。

- **目标层不冲突**：TTCF、帧时间 p99、metaspace 曲线、故障归因率
  采样于生命周期的**不同状态区间**，彼此不争夺同一笔预算。
  把它们并列成 KPI 去取舍，是把时间轴误读成了资源池。
- **执行层有冲突**：优化不消灭成本，只**搬移**成本。一项把成本从
  `DISCOVERING` 搬到 `RUNNING` 的改动，会和稳态优化正面相撞。
  冲突不在目标，在成本流向。

所以真正的管理对象不是"优化项清单"，而是**成本流**。本文把这个流
记成账本，并给出一条硬规则：**任何未申报成本流向的优化不得合并。**

---

## 1. 坐标轴：两套九态，两个粒度

平台有两套状态机，它们不是重复，是同一过程的两级分辨率。

**平台级**（`BootstrapState`，一次进程一条线）：

```text
CREATED → DISCOVERING → PREPARING → LOADING → BOOTSTRAPPING → RUNNING
                                                                    ↓
                          FAILED ←──────────────────── STOPPING → STOPPED
```

**组件级**（`LifecycleState`，每个 Mod 一条线）：

```text
DISCOVERED → RESOLVED → LOADED → INITIALIZED → REGISTERED → RUNNING
                                                                ↓
                                    FAILED ←────── STOPPING → STOPPED
```

映射关系是**多对一**的：`BOOTSTRAPPING` 期间，不同 Mod 可能分别停在
`LOADED`、`INITIALIZED`、`REGISTERED`。这一点决定了归因的难度——
平台级时间戳只能回答"慢在哪个阶段"，回答不了"慢在哪个 Mod"。
后者必须由组件级时间线提供。

> **状态区间不等于启动步骤。** 真实的启动流程是 `LoaderMain.launch()`
> 里的一串顺序调用，`BootstrapState` / `LifecycleState` 描述的是**组件视图**，
> 并不逐条驱动那串调用（真正的状态推进点在 `Runtime.start()` 与
> `Scope.shutdown()`）。因此基线按**步骤**采集，再映射到状态区间；
> 反过来做会得到一张与代码对不上的表。

> 状态集合以 `org.loader.api.lifecycle.LifecycleState` 与
> `BootstrapState` 为准。README 中早期描述的五态（`LOADING` /
> `INITIALIZING` / `ACTIVE` / `SUSPENDED` / `UNLOADED`）已不对应代码，
> 不要作为设计依据。

### 1.1 每个状态的预算归属

| 状态区间 | 预算维度 | 用户何时感知 | 可否被借贷 |
|---|---|---|---|
| `CREATED → DISCOVERING` | 墙钟、I/O 次数 | 每次启动 | 可（移到安装期） |
| `DISCOVERING → PREPARING` | 墙钟、内存峰值 | 每次启动 | 可 |
| `PREPARING → LOADING` | 墙钟、metaspace | 每次启动 | 可 |
| `LOADING → BOOTSTRAPPING` | 墙钟、metaspace、线程数 | 每次启动 | 可 |
| `INITIALIZED → REGISTERED` | 墙钟 | 每次启动 | 可 |
| `RUNNING` | p99 帧/tick、分配率、RSS | **持续整个会话** | **不可** |
| `STOPPING → STOPPED` | 墙钟、残留线程/句柄/类 | 每次退出 | 可 |
| `FAILED` | 归因精度、恢复时长 | 出事那一刻 | 可 |

`RUNNING` 那一行的"不可"是这张表的全部意义。启动多花 3 秒，用户
每次付一次；稳态多 1ms/帧，用户每秒付 60 次。**任何搬向 `RUNNING`
的成本，无论起点多廉价，都是负收益。**

## 2. 成本守恒：四条搬移规则

一项优化改动必须在 PR 描述里填四个字段：`costFrom`、`costTo`、
`metric`、`guard`。四条规则按严重度排列：

**R1 · 出口唯一。** 唯一无损的成本出口是**生命周期之外**——构建期、
安装期、首次启动后的一次性预热。AOT 类加载归档、反射桥接清单的
构建期校验、资源索引的安装期建立，都属于这一类。这不是"把成本藏起来"，
而是把它移到用户不计时的时间窗里。

**R2 · 禁止向 `RUNNING` 借贷。** 惰性化是最常见的违规形态：把初始化
成本从 `INITIALIZED` 挪到"第一次用到时"，而"第一次用到"往往就是第一帧。
这类改动必须证明触发点不在热路径上，否则拒绝。

**R3 · 资源借贷必须明示。** 缓存换 CPU 是可接受的，但要在账本里写成
"RSS +N MiB 换 p99 −M ms"，而不是只报收益。8 GiB 机器上，内存不是
免费变量。

**R4 · 并行化只改墙钟，不改总量。** 并行缩短 wall clock，CPU 总量不变。
并行度超过物理核数时，上下文切换与 GC 压力会把收益吃回去。
按 [ADR-0010](../decisions/0010-observe-before-parallelize.md)，并行化
必须先有基线观测，且必须先缩短关键路径再谈加线程。

## 3. 三个反例：看起来赚了，其实只是搬了

**惰性资源解析。** 启动时不解压资源，首次访问时解压。启动数字漂亮，
代价是第一帧的 I/O 抖动——而第一帧恰好是玩家最敏感、最不应该出现
卡顿的时刻。若采用，必须配合"后台预热 + 首帧前完成"的折中。

**全量元数据缓存。** 扫描期把所有 `mod.json` 解析成完整对象图常驻。
依赖图求解确实变快，但 200 个 Mod 的对象图在启动后就没有用了。
正确做法是求解完即丢弃，只保留拓扑序与校验结论。

**多线程扫描。** 扫描是 I/O 密集的，看似天然适合并行。但 JAR 的
central directory 读取很快，真正的瓶颈往往是解压与哈希校验；
把这两件事并行，收益被磁盘队列深度截断，还引入了一组新的线程
生命周期要管。**先测关键路径，再决定是否并行。**

## 4. JIT 的真实税负在哪里

上一节谈的是显性成本。还有一笔隐性成本，是这个架构特有的，必须
单独说清楚——否则"更快"这个承诺永远无法兑现。

ClassLoader 拓扑是：`AppCL`（平台）→ `MinecraftClassLoader` → 每个
Mod 一个 child-first 的 `ModClassLoader`。由此产生两种方向完全相反
的调用：

| 调用方向 | 类型 profile | 税负 |
|---|---|---|
| Mod → Minecraft（`net.minecraft.*`） | MC 类**全局唯一**，单态 | 无额外税 |
| 平台 → Mod 扩展点（ABI 接口） | N 个 Mod 各有一份实现，**megamorphic** | 无法内联、无法 CHA |

所以"跨 ClassLoader 就一定慢"是错的。真正的税集中在**平台回调
Mod 的那一侧**：每个扩展点都是一次面向 N 个未知实现的虚调用。

三条缓解路径，按收益排序：

1. **按单一实现约束热点扩展点。** 一个扩展点允许多个消费者时，把它
   降级为"批量数据传递"；只允许一个实现时，热点退回单态。
2. **派发的多态性按类衡量，不按实例。** JIT 的类型 profile 是类级别的。
   如果所有 Mod 的事件派发都经过**同一个** `EventDispatcher` 类的不同
   实例（内部持有 `MethodHandle[]`），调用点在 JIT 眼里依然是单态的。
   反过来，为每个 Mod 生成一个 `XxxDispatcher` 类，就把单态变成了 N 态——
   这是"代码生成越多越快"的典型误判。
3. **`REGISTERED` 是唯一的固化窗口。** 此时 `RUNNING` 尚未开始，可以
   自由地把订阅表、字段句柄、桥接引用编译成 `MethodHandle` 并封进
   `@Stable` 字段。错过这个窗口，之后每一帧都要为查找付费。

> 第 2 条与 [ADR-0011](../decisions/0011-platform-owned-asm-transformation.md)
> 有关：平台自有 ASM 改写能力应当用于**减少**类型多样性（合并派发入口），
> 而不是为每个 Mod 生成专属分派类。

## 5. 生命周期本身也是被优化对象

前面的坐标轴把生命周期当作容器。还有一层：状态机自身的开销与可观测性。

**转换必须 O(1) 且无分配。** 一次状态转换不应创建事件对象、不应
`List` 拷贝、不应字符串拼接。合法转换表应当是编译期确定的二维表
（或 `switch`），非法转换直接抛 `IllegalStateTransitionException`，
不需要查表失败后的兜底路径。

**转换必须可审计。** 维护一个定长环形缓冲（容量与
`PerformanceMonitor` 的 600 槽一致），记录 `(timestamp, modId, from, to)`。
崩溃时不依赖日志刷盘——直接在内核崩溃钩子里把环形缓冲 dump 出去。
这是 `FAILED` 归因精度的物理基础。

**`FAILED` 必须携带足够上下文。** 只记录异常类型没有价值。需要的是：
失败发生在哪个阶段、哪个 Mod、哪些资源已注册（因而必须逆序释放）、
以及该 Mod 的 `ModClassLoader` 是否仍可达。

**tick 线程的上下文追踪可以是零成本的。** `TickEngine` 强制校验驱动
线程唯一，因此"当前正在执行哪个 Mod 的任务"可以用一个普通字段表达，
不需要 `ThreadLocal`。这是架构约束换来的性能——单线程是缺陷，
但在这里是资产。看门狗（deadline 巡检）触发时，读这个字段就完成了归因。

## 6. 执行顺序：依赖图，不是优先级表

"全选"作为目标集合成立，但六件事之间有真实的依赖，不能并行推进：

```text
(1) 基线观测
      │  没有基线，账本无法判断平衡与否
      ├──→ (2) 出口搬运：AOT 归档 / 构建期校验 / 安装期索引
      │          无风险，且立刻释放启动预算
      ├──→ (3) 稳态零分配：事件派发 / tick 采样 / 快照
      │          有现成护栏（8 B/tick），可回归
      └──→ (4) 注册期固化：MethodHandle 预编译 / @Stable 字段
                  │
                  └──→ (5) 故障圈定：环形缓冲 / 看门狗 / 影子栈
                              │
                              └──→ (6) 关闭回收审计
```

**(6) 依赖 (4)** 是最容易被忽略的一条：注册期固化的 `MethodHandle`
若持有 `ModClassLoader` 的强引用，会让类永远无法卸载。
`ClassLoaderLeakTest` 目前能挡住"Scope 关闭后 CL 仍可达"，
但挡不住"CL 可回收、而平台侧缓存仍持有它加载的类"。
固化与卸载是一对必须同时设计的机制。

**(5) 依赖 (1)** 的理由不同：归因精度需要用真实崩溃样本校准，
没有观测数据就只能猜。

**当前进度**（截至 `0.1.0`）：

| 步骤 | 状态 | 落点 |
|---|---|---|
| (1) 基线观测 | 已完成 | `StartupTimeline` |
| (2) 出口搬运（AOT） | **未做**，需一次真实训练运行 | 见 §7.1 |
| (3) 稳态零分配 | 既有护栏，未新增 | `HotPathBenchmarkTest` |
| (4) 注册期固化 | **未做**，见下 | — |
| (5) 故障圈定 | 部分完成（归因 / 看门狗 / 墓碑），安全模式未做 | `TickWatchdog`、`LifecycleAudit` |
| (6) 关闭回收审计 | 已完成 | `ShutdownAudit` |

**(4) 为什么先不做。** 注册期固化要动的是事件派发的调用点形态
（单实现约束、`MethodHandle` 预编译、`@Stable` 字段）。这类改动
**没有基准就无法证明是优化**：把虚调用换成 `MethodHandle` 在解释执行
和 C1 下可能更慢，只有在 C2 稳态、且调用点真的 megamorphic 时才赢。
按 ADR-0010，动手之前需要先有"派发点的实际多态度"数据 ——
而那正是 (1) 才能提供的。先做 (4) 等于凭直觉改热路径。

**生态迁移（Fabric API 映射、移植助手、兼容 shim）不在这个图里。**
它与上述技术项无依赖，但它是"用户为什么选你"的**真正瓶颈**——
详见第 8 节。

## 7. 各段的攻坚项与判据

### 7.1 启动段（`CREATED → REGISTERED`）

**采集手段已就位**：`org.loader.runtime.diagnostics.StartupTimeline`。
`LoaderMain` 在每个阶段末尾打一个点，顺序为
`parseArgs` → `loadConfig` → `constructLoader` → `ensureMinecraft` →
`locateGame` → `createGameClassLoader` → `scanMods` → `discoverManifests` →
`resolveDependencies` → `reportDiscovery` → `runtimeStart` →
`validateVersionBindings` → `createModClassLoaders` → `installServices` →
`initializeMods` → `declareContent`。逐 Mod 初始化以 `initializeMods`
区间展开（子项名为 `init:<modId>`），兄弟超过 8 个时只展示最慢的若干并
聚合其余。报告在把控制权交给 Minecraft **之前**输出，异常路径先落盘再抛出。

| 攻坚项 | 成本去向 | 判据 |
|---|---|---|
| AOT 类加载与链接归档 | 构建期 / 安装期 | TTCF 相对基线的降幅 |
| JAR 只读 central directory，不解压 | 无 | 扫描期读字节数 |
| 依赖图求解后立即丢弃对象图 | 无（负成本） | 求解后常驻对象数 |
| 三元组校验与依赖求解重叠 | 无 | 关键路径长度 |
| 并行发现（**仅在有基线后**） | 峰值 CPU | wall clock，且 CPU 总量不变 |

平台的独特优势在于：**只有加载器自己知道它将要加载什么**。这个信息
在 Fabric 的启动路径上拿不到——那里被 LaunchWrapper 的遗产绑死了。
所以 AOT 不是"抄一个特性"，是把信息优势变现。

**这一项尚未实施，原因不是难，而是它必须由一次真实运行产出。**
AOT 归档不是编译产物，是训练产物：得让 JVM 跑完一遍启动（最好进到世界），
把类加载与链接的结果录下来。本仓库的构建环境里没有这条链，因此只能
把命令固定下来，等一次带客户端的运行：

```bash
# 1) 训练一次，产出归档（每个 JDK 版本 / 类路径指纹各一份）
java -XX:AOTCacheOutput=build/aot/mili.aot \
     -cp mili-0.1.0-mc26.2.jar org.loader.loader.LoaderMain <gameDir> ...

# 2) 分发时带上归档，启动时使用
java -XX:AOTCache=build/aot/mili.aot -cp mili-0.1.0-mc26.2.jar ...
```

三个约束必须一起接受，否则收益会变成负的：

- **归档与 JDK 版本、类路径指纹绑定。** 不一致时 JVM 静默忽略它 ——
  不会报错，但收益归零。因此它必须与平台版本一同发布、一同升级。
- **训练用的 Mod 集合决定命中率。** 用官方示例 Mod 训练，对玩家的
  200 个 Mod 包几乎无效。可行的折中是只覆盖平台自身 + ABI + 桥接层
  （这部分对所有人相同），Mod 部分留给各自的首次运行。
- **`-XX:AOTCache` 是启动参数。** 平台不能替用户改启动命令行 ——
  启动脚本必须显式写上去。这与"无 Agent、不改启动参数"的既有承诺
  有张力，需要一次明确的设计取舍，而不是悄悄塞进去。

### 7.2 稳态段（`RUNNING`）

| 攻坚项 | 判据 |
|---|---|
| 事件派发零分配 | 已有护栏：`HotPathBenchmarkTest`，≤ 8 B/次 |
| 派发入口合并为单一类 | 派发循环的 JIT 编译日志中 `invokeinterface` 不出现 megamorphic |
| tick 采样零分配 | 已有护栏：≤ 8 B/tick |
| 快照合并窗口 | 已有护栏：250 ms 内同一实例 |
| Mod 级 tick 成本归因 | 已实现：能回答"这 3ms 是哪个 Mod 花的" |

前四项已有护栏，第五项**已补齐**。实现路径与最初的设想不同，值得记录：

原计划"在 `TickContract` 的任务执行点按 `modId` 累加"，但那个方案要求
调用方在提交任务时提供 `modId` —— 要么污染整条 ABI，要么要求 Mod 配合。
两者都与"观测不拦截"冲突。实际做法是**按类加载器归因**：
`TickTask` 在构造时记下 `work.getClass()`，`ModOwners` 把它反查到
`ModClassLoader` 对应的 modId（`ClassValue` 缓存，一个类只解析一次）。
Mod 什么都不用做。

归因结果由 `ModAttribution` 累加，随 `TickEngine.diagnostics()` 输出。
未归因（平台自身开销）永远单列一行——把它藏起来，读者会以为所有时间
都属于 Mod。

### 7.3 故障段（`FAILED`）

| 形态 | 现状 | 缺口 |
|---|---|---|
| 未捕获异常 | 捕获、记录，归因到 Mod 已具备 | — |
| 失控（死循环 / 超时） | `TickWatchdog`：超过阈值吐出**归属 + 驱动线程真实栈** | 不终止任务（刻意，见下） |
| JVM 崩溃 / 进程被杀 | 启动失败路径把审计环追加进 `logs/mili-audit.log` | 无安全模式、无 native crash 钩子 |

**为什么不做"超时就杀掉"。** `Thread.stop` 会在任意指令边界抛
`ThreadDeath`，把半改完的世界状态留在内存里——那比卡住更难排查。
平台能安全做的只有两件事：说清楚是谁，以及下次启动跳过它。
前者已实现，后者（安全模式）仍是缺口。

**墓碑的形态。** 不是完整日志，而是一段定长环形缓冲（`LifecycleAudit`，
256 条）落到 `logs/mili-audit.log`。理由很实在：崩溃时大日志的最后
几行往往不可靠（缓冲区没来得及刷），而这一小段历史是同步写出去的。
**只在失败时落盘**——正常启动也写，只会让 `logs/` 变成没人看的垃圾堆。

**仍缺的是跨进程的部分。** 现在的墓碑需要人来读。要让加载器自己读它、
自动禁用上次崩掉的 Mod，需要一个稳定的 tombstone 格式 + 启动期读取逻辑，
而且判断必须发生在**新进程**里——在崩溃现场做复杂判断的设计，
在真实现场一定失效。

### 7.4 关闭段（`STOPPING → STOPPED`）

已有三条不变量（有主、可撤销、关后拒用）与逆序释放。
新增的判据只有一条：**帧内预算**——关闭不应阻塞主线程超过一帧。
逆序释放本身可能触发阻塞 I/O（ZIP 关闭、原生库卸载），
需要把阻塞部分挪到后台并以"关后拒用"保证正确性。

**回收审计已实现**（`ShutdownAudit`），口径刻意保守：

| 测量 | 时点 | 为什么 |
|---|---|---|
| 线程基线 | Mod 初始化**之前** | 之后抓等于把 Mod 新建的线程算进基线，增量恒为 0 |
| 已加载类数 | `ModClassLoader` 关闭**之前** | 关闭后 `loadedClasses()` 是空集，会显示"每个 Mod 0 个类" |
| 关闭后线程 | `runtime.close()` **之后** | 之前测到的只是"还没关完" |

三条时点都是"测早一步就测不到"。报告**只列举不判定**：把"线程数增量
必须为 0"写成硬断言会在真实客户端大量误报（Minecraft 自己在关闭期
也会建线程），误报多了这条审计就会被整体关掉，连报告价值都没有。
平台自有线程（`mili-watchdog` 等）按前缀排除，否则看门狗会因为
"在基线之后启动"而被当成泄漏。

## 8. 账本之外：为什么性能不是决定因素

一个快 30% 但 Mod 覆盖率 5% 的平台，玩家不会选。这不是"优化"能
解决的问题，但它是"用户为什么选你"的真实答案，所以必须写在这里，
避免账本做得漂亮却指错方向。

**冷启动的真正成本是迁移工时，不是运行开销。** 所以优先级最高的一项
投入，是把 Fabric API 的常见调用映射到 Mili ABI 的半自动改写工具，
以及一份逐条标注"能映射 / 需重写 / 无对应"的对照表。

这与"不兼容 Fabric"的哲学有张力，但可以化解：**拒绝隐式兼容，
不等于拒绝降低迁移成本。** 显式声明的移植助手不违反任何一条
设计原则——它把"你要重写"变成"这里有 70% 是机械改写"，
而机械改写恰恰是显式性的最佳体现。

## 9. 记帐格式

每项优化在 PR 描述里附一段：

```text
costFrom: BOOTSTRAPPING (class linking)
costTo:   INSTALL (AOT archive generation)
metric:   TTCF, cold start, 100 mods
delta:    TBD after baseline
guard:    LaunchTimeBaselineTest (新增)
risk:     归档与 JDK 版本绑定，升级 JDK 需重新生成
```

四项缺一不可。`costTo == RUNNING` 时，PR 必须额外给出"触发点不在
热路径"的论证，否则不合并。

## 10. 已知边界

1. **本文的预算阈值大多未定。** 除已有护栏外，标 TBD 的项需要先做
   基线测量（ADR-0010）。先写规则、后填数字，比先拍数字、后补规则
   更安全——后者会让人为了达标而改测量方法。
   采集器（`StartupTimeline`）已经就位，但**基线必须在真实客户端跑一次**
   才有意义：构建机的 CPU 与磁盘都比玩家机器好，用它当基线会让所有
   优化看起来都没效果。建议取中端配置（8–16 GiB 内存、四核）的一次
   冷启动 + 一次热启动，作为第一组数字。
2. **AOT 归档与 JDK 版本绑定。** 升级 JDK 必须重新生成，不能随
   平台版本复用。这条约束会影响发布流程，需要单列。
3. **`RUNNING` 的"不可借贷"有一条例外**：首次进入世界的区块生成
   与着色器编译。它们是游戏本身的固有成本，平台能做的是把 Mod 侧
   的首次成本排在它们之前完成，而不是与其重叠。
4. **归因到 Mod 需要 Mod 走 `Scheduler`，但平台不强制。**
   **决策：不拒绝加载自建线程池的 Mod。** 把"所有工作必须经过 `Scheduler`"
   写成 ABI 硬约束，会让生态在第一天就窄掉一大半 —— 大量现成代码
   （异步 IO、渲染后处理、第三方库回调）本来就自带线程，要求它们为了
   可诊断性重写，是把平台的洁癖成本转嫁给 Mod 作者。
   代价必须承认：这类 Mod 的 tick 成本会退化为"未归因"。平台的做法是
   **在启动报告里标注它，而不是拦下它** —— 观测与准入是两件事，
   把它们捆在一起，就变成了用可诊断性换取生态规模。
   若将来确实需要强约束，正确的位置是"新 Mod 模板默认走 Scheduler +
   文档写明收益"，而不是加载期拒绝。
5. **时间线起点是 `main()`，不含 JVM 引导。** 类加载器初始化、CDS/AOT
   归档解析、`-Xmx` 相关的前期准备都在 `main` 之前发生。要覆盖那一段
   需要 `-Xlog:startuptime` 或 AOT 归档的自带统计，属于另一个采集面，
   不在本时间线的职责内。**因此"总 1842 ms"不等于玩家的 TTCF 增量**——
   它只说明平台自己花掉了多少。
