# 2026-10-05

## 修复 CI 反编译流水线从未真正执行 + 首次成功发布 v26.2

### 根因（三层，逐层暴露）
1. `test_client/` 在 .gitignore 中，Minecraft JAR 从未入库（仓库仅 400KB）。
   CI 的 `find . -path '*test_client*'` 永远找不到 → `found=false` →
   prepare/decompile/generate 全部 SKIPPED，且被 `onlyIf` 静默吞掉。
2. 由此 `minecraft.json` 从未被打进 JAR，`verifyPlatformJar` 报
   `META-INF/mili/minecraft.json missing`，release 在最后一步失败。
3. **关键坑**：`File(path).absoluteFile`（`resolveMinecraftArtifact` 与
   `minecraftArtifactSha256`）以 **Gradle daemon 的工作目录**
   （`~/.gradle/daemon/<ver>/`）为基准，而非项目目录。
   即使 JAR 已下载、`MINECRAFT_ARTIFACT=test_client/26.2.jar` 正确传入，
   仍解析成 `<daemon>/test_client/26.2.jar`（0 字节）→ 依旧 SKIP。
   这是"看起来都配对了却还是跳过"的真正原因。

### 改动（仅限构建报错与发布必要）
- ci.yml / release.yml：从 piston-meta 官方清单按 `minecraftVersion` 解析
  client 下载 URL，校验官方 SHA-1，导出**绝对路径** MINECRAFT_ARTIFACT。
  废弃原先探测仓库内 `test_client/` 的逻辑。
- mili-minecraft-integration：`resolveMinecraftArtifact` 相对路径锚定到
  projectDirectory；CFR `maxHeapSize = "4g"`（全量 MC 用默认堆会 OOM）。
- mili-loader：`minecraftArtifactSha256` 同样锚定项目目录；
  移除 skip-path 下失效的 `artifactSha256` 断言。

### 验证结果（v26.2 已发布）
- CI 三 job 全绿；真实反编译：10952 classes → 7055 sources →
  37 events / 10 registries（修复前全是 SKIPPED）。
- Release 产物 `mili-0.1.0-mc26.2.jar`（283,989 B，258 entries），
  SHA256SUMS 校验 OK，minecraft.json 指纹
  `40896ee9...290` 与官方 26.2 client.jar 完全一致。

### 重要结论：发布物是"加载器"，不含 Minecraft 本体
- JAR 内 `net/minecraft` 条目 = **0**，`org/loader` = 249，`.java` = 0。
- 这是 ADR 0005「Minecraft Is Host, Not Kernel」的设计刻意选择，
  也规避 Mojang 再分发条款；反编译源码仅作构建期元数据输入。
- 要真正"启动完整 Minecraft"，需 loader + 用户自备正版 MC 安装，
  由 `MinecraftDiscovery` 发现后以 URLClassLoader 同进程加载
  （入口 `net.minecraft.client.main.Main`）。
- 目前仓库无 distribution/application 插件，README 提到的 distTar/distZip
  与实际不符——如需开箱即用分发包需另行实现（本次未改，超出授权范围）。

## 新增 mili-installer + distribution 打包（第二轮，全做完）

### 动机
发布页 JAR 仅 285KB / `net/minecraft` 条目为 0 —— 是纯加载器，不是游戏。
用户要求「下载发布页即可启动完整 Minecraft」。README 早已宣传
distTar/distZip/bin/mili-loader，但构建脚本里从未实现。

### 关键决策：不把 MC 合并进 jar
合并 MC 类违反 Mojang EULA，且合并了 39MB client.jar 仍缺 88MB libraries
与 480MB assets，照样跑不起来。改为：发布加载器 + 安装器，首次运行从
Mojang 官方 CDN 拉取并逐个校验 SHA-1。分发包维持 KB 级。

### mili-installer（零第三方依赖，仅 JDK）
- `Json` — 手写 RFC 8259 解析器（用户可能只有 JRE，不能引入 Gson）
- `MojangMetaClient` — manifest → version JSON，不碰任何认证端点
- `VerifiedDownloader` — 流式 + SHA-1 + `.part` 原子 rename + 幂等跳过
- `PlatformRules` — 运行时求值 77 个带 rules 的 libraries 与 natives classifier
- `LibraryInstaller` — 标准 Maven 布局 + natives 解压到 `natives/<os>/`
- `AssetInstaller` — 虚拟资源树，8 线程，约 480MB
- `InstallOrchestrator` / `InstallerMain` — 幂等 CLI

### 踩过的坑（重要）
1. **Mojang 元数据类型不一致**：真实 26.2 的
   `javaVersion.majorVersion` 是**数字 25.0**，旧清单是字符串 `"25"`。
   用 `Json.str` 读会得 null → 回退 "8" → 提示「26.2 建议使用 Java 8」。
   新增 `Json.strOrNumber` 同时兼容两种编码。
2. **Kotlin DSL 打包布局**：`into("README.txt")` 会让 Gradle 把它当**目录**，
   产出 `README.txt/README.txt`；裸 `into("mods")` 后紧跟 `from(...)` 会让
   后续 from 落到兄弟层级。正确写法：`into(root){ into("core"){from(..)}; from(file) }`。
3. **断言位置**：布局断言只放在 ci.yml 时，release job 照样发出坏包。
   现在 release.yml 也断言，并在 publish 前执行。
4. **本机限制**：用户 8G 内存，禁跑 java/gradle（会卡机）。但
   `javac` 单文件 + 反射 MiniRunner 可用于快速验证；`./gradlew distTar
   --offline` 也只需 43s，可用来验证打包布局（已获用户默许此次使用）。

### Mojang rules 语义（曾写错断言）
顺序扫描，首个匹配决定，**无匹配则默认 allow** —— 所以「disallow 写外平台」
根本不生效，排除必须靠匹配本机的 rule。

### 验证结果
- CI 4 个 job 全绿；42 个 installer 单测通过。
- smoke test 真实连上 Mojang：131 个库、client 37.4MiB、assets 458MB。
- 发布页 v26.2 现有 4 个资产，SHA256SUMS 全 OK；tar.gz 布局正确，
  installer 28 个类已合入平台 JAR，MC 指纹与官方一致。

### 用户决策

### 字节码委托的实证结论（全部在真实 MC 26.2 + libraries 上跑通）
这是本次最有价值的产出 —— **不要凭记忆写反射，必须实测**：

1. `Bootstrap.bootStrap()` **必须先调用**，否则
   `IllegalArgumentException: Not bootstrapped (called from registry minecraft:game_event)`。
2. `SharedConstants.tryDetectVersion()` **必须先调用**，否则
   `IllegalStateException: Game version not set`（由 bootStrap 内部触发）。
3. **`ClassLoader.defineClass` 被模块系统封锁**（需 `--add-opens java.base/java.lang`），
   用户双击启动不会有该参数 → 不可用于生产。
4. **可用替代：`MethodHandles.privateLookupIn(Block.class).defineClass(bytes)`**
   —— 实测 `setAccessible` 可用，**无需任何 --add-opens**。
5. **`Lookup.defineClass` 要求生成类与 lookup 类同包**：
   `IllegalArgumentException: X not in same package as lookup class`。
   因为 lookup 来自 `Block`，生成类必须放 `net/minecraft/world/level/block/`。
6. 26.2 的钩子不在 `Block` 而在父类 `BlockBehaviour`，且签名已重构：
   - `tick(BlockState, ServerLevel, BlockPos, RandomSource)`
   - `neighborChanged(..., Block, Orientation, boolean)` ← 26.2 多了 2 参
   - `useWithoutItem(...)` / `useItemOn(...)` 取代了旧的 `use(...)`
   - `getDestroyProgress(BlockState, Player, BlockGetter, BlockPos)`
7. 方块属性：`BlockBehaviour.Properties.of()` 静态工厂 → `noOcclusion()` / `strength(float)`
   / `randomTicks()` / `lightLevel(...)` 等链式。
8. 实例化普通 Block 仍会 `Block id not set`（`BlockBehaviour.<init>` 要求 id），
   因为尚未注册进注册表 —— 属流程问题，非架构问题。
9. 探针自身两个 bug（记录以免重犯）：`Class.forName` 要**点号**（斜杠是 ASM 内部名）；
   classpath 用相对路径时 JVM 工作目录不匹配会静默找不到 MC 类。

### 26.2 类结构变化（与旧版本不同，凭记忆会写错）
- `net.minecraft.world.level.item.Items` **存在于 jar 内**，但 `javap` 在缺
  DataFixerUpper 等依赖时报「找不到类」→ 探测时必须带完整 libraries classpath。
- 注册表走 `ResourceKey<Registry<T>>` 模式：`Registries.BLOCK`、`BLOCK_ENTITY_TYPE` 等。

## 全面审计 + Phase 2~7 实施（第三轮：把原型推进为真实平台）

### 审计发现的真相（评分被高估了）

用户给的评分里**ClassLoader 6/10 与 Tick 4.5/10 实际都偏乐观**：

1. **ClassLoader 是坏的，不只是弱**：`ModClassLoader` 给每个 Mod 平铺完整
   Minecraft classpath，且与 gameCL **平行无关联** → Mod 拿到的 MC 类与游戏里的
   **不是同一个 Class**，任何 `Class.forName("net.minecraft...")` 得到的对象传给
   游戏必然 `ClassCastException`。也就是说 **Mod 根本无法操作 Minecraft**。
   `ModClassLoaderManager` 恒传 `parent=null`，依赖链是死代码。
2. **Tick 集成形同虚设**：`ClientTickPoller` 以 10Hz 轮询 `level.getGameTime()`
   "推测" tick。后果：轮询粒度≠20TPS、轮询线程≠MC主线程、
   `level==null`（单人世界）时 tick 停摆、异常被吞。
   `level.getGameTime()` 多人下与服务器 tick 不同步 —— **不存在可用的轮询方案**。
3. **`TickContract` 是纯静态类**（无法实例化），只有 2 个 record + 1 个 enum，
   无法表达"阶段推进"。配套 `TickContractTest` 断言的是 `50/2=25`、`50/4=12`
   这类字段算术 —— **虚假绿灯**。
4. **Scheduler 优先级是假的**：优先级队列取出后交给 FIFO 线程池，排序白做。
5. **`submitRepeating` 用 `Thread.sleep` 占池线程** → 周期任务占满线程池致饥饿。
6. **`verifyPlatformJar` 统计 mcClasses 但只打日志不报错** → 分发边界无约束。
   CI 的 layout 检查也没有任何禁止 Minecraft 的规则。
7. **25 处版本字面量兜底**（`?: "0.1.0"`）是版本漂移根源。

### 关键架构决策（用户批准后执行）

**ClassLoader 拓扑**（`docs/architecture/CLASSLOADER.md`）：
`MinecraftClassLoader` 成为**唯一**定义 `net.minecraft.*` 的地方，
`ModClassLoader` 以它为 parent 且**只含自身代码源**。
parent 是 gameCL 而**不是依赖 Mod** —— 否则 A 卸载会影响 B 已链接的类，
且循环依赖无法处理。跨 Mod 访问走 `ClassVisibility.export()` 显式声明。
`ClassVisibility` 单点定义 FORBIDDEN/PARENT_FIRST/SELF_FIRST 三态。

**Tick 契约**（`docs/architecture/TICK_ENGINE.md`）：
`TickContract` 改为可实例执行信封 + 新增 `TickEngine`。
责任明确到类：TickEngine 是唯一 `advance()` 调用方、唯一在屏障
`awaitAllTasks()` 处等待、捕获异常后 `contract.fail()` 而非逃逸。
`endTick()` 自动补齐未推进的后续阶段。
**异常不逃逸、失败隔离**是核心性质：Mod 抛异常不能打断 tick 循环。
`MinecraftTickSource` 窄接口的用意 —— **tick 正确性可在不启动 Minecraft
的情况下完整验证**。

**未采用**：为省事保留轮询方案。它在 20 TPS 下不成立，不是能优化的问题。

### 顺带修掉的真实缺陷
- `BootstrapState` 九态状态机（迁移受校验，跳步/回退抛异常）
- `bootstrap.fail()` 逆序释放外部资源 + 关闭 Scope
- `ScheduledTask` 改为 `implements Runnable`，线程池直接从优先级队列取
- `submitRepeating` 改用独立守护计时器，不占工作线程
- `distributionBoundaryCheck` + CI shell 双实现独立扫描
  （刻意不复用 Gradle 逻辑，两套实现同时通过才算数）
- 版本单一来源：根项目 `requireNotNull(findProperty(...))`，
  子项目经 `rootProject.extra` 读取；`verifyVersionConstants` 校验
  `VersionInfo` 常量与 `gradle.properties` 一致

### 文档防误判机制
旧文档（含极具误导性的 `execution/CURRENT_IMPLEMENTATION_STATE.md`）
全部移入 `docs/history/` 并加横幅警示；`docs/architecture/CURRENT.md`
成为唯一当前状态来源。

### 诚实结论
**当前仍无任何测试真正启动 Minecraft**。全部是纯 JVM 测试。
`ReflectiveMinecraftTickSource` 目前只是骨架，尚未实现对 26.2
真实 tick 方法的定位与转发。这是 Tick 从"协议正确"到"真实生效"的最后一环，
也是下一步第一优先级。

**本机限制**：用户禁跑 java/gradle（8G 内存会卡机），
故本次全部改动**未经编译验证**，需 CI 兜底。

### 测试结果

跳过的 4 项是设计如此：无 Minecraft 输入时的降级路径断言，CI 不该有 MC 依赖。

### 26.2 注册时序：第四条硬约束（新增，实测字节码确认）
`MappedRegistry.freeze()` 偏移 114–117：
```java
if (!unregisteredIntrusiveHolders.isEmpty())
    throw new IllegalStateException("Some intrusive holders were not registered: ...");
```
`Block.<init>` 会自动 `createIntrusiveHolder(this)` 登记进去，**只有 `Registry.register(...)` 会移走**。
→ **任何"造了但没注册"的方块都会让整个游戏启动失败**，且错误消息是一串
`Block{[unregistered]}`，完全不指向是哪个 Mod 造成的。
`RegistrationPhase.closeRegistryWindow()` 现在会 drain 这个 Map 并报出责任方清单。
连带修掉的三个"造了不注册"入口：`selfCheck()`、`GeneratedBlockProbe.newBlock()`、测试的 `blockFor(...)`。

### 三个此前被测试假象掩盖的真实缺陷

**1. bootstrap 状态是全局静态，但实际归属每个游戏 ClassLoader**
`SharedVersionGate.DETECTED` / `RegistrationPhase.FLAGGED|COMPLETE` / `BootstrapGate.DONE`
原本都是平台 CL 上的单个静态字段，而它们描述的事实（`Bootstrap.isBootstrapped`、
注册表 frozen）都由游戏 CL 定义。同 JVM 内跑两个游戏实例时，第二个会永久锁死注册窗口。
已改为按 ClassLoader 隔离（新增 `GameSessionState`，弱引用键）。

**2. 测试的游戏 ClassLoader 父加载器为 null，没有复现生产拓扑**
`new URLClassLoader(urls, null)` 让游戏 CL 完全看不到平台类，导致生成的 `MiliBlock`
解析不到 `BehaviourDispatch`，抛 `NoClassDefFoundError`。
但生产拓扑（`MinecraftClassLoader`）的 parent 就是平台 CL，且显式把 `org.loader.*` 委派给 parent。
→ 这个差异会让测试**验证一个生产环境不存在的故障**，进而误改本来正确的实现。
已新增 `GameTestClassLoader`（测试源集）复刻生产加载器的三条委派规则。
注意：不能直接依赖 `mili-loader` 里的 `MinecraftClassLoader`，会造成模块循环依赖。

**3. `MinecraftBootstrap.start()` 曾有"自动补齐中间阶段"的便利分支**
从 CREATED 直接补齐到 BOOTSTRAPPING 再 RUNNING —— 把跳步迁移伪装成合法迁移，
与 `BootstrapState` 类注释里"跳步或回退都会抛 IllegalStateTransitionException"直接矛盾。
后果：忘记调用 `beginDiscovery()` 这类集成错误永远不会暴露，游戏会在没做发现/准备/加载的情况下启动。
已删除该分支，`bootstrap_startAndStop` 测试改为走完整序列。

### 26.2 其他 API 事实
- `BlockBehaviour.destroyTime` **字段已不存在**，改为 `defaultDestroyTime()` **方法**。
  测试里 `readFloat(block,"destroyTime")` 永远读不到 —— 这就是该测试"假绿"的原因。
- `BlockSpec.hardness` 默认值是 **3.0f**（Minecraft 默认），不是 0。
- 硬度的**负值必须显式映射成 -1**。原实现对负值"跳过 strength()调用"，
  结果保留默认 0 —— 把"坚不可摧"悄悄变成"一戳就碎"。已修。
- 生成类的 `behaviour` 字段类型必须是 `int` 而非 `BehaviourDispatch$Handle`：
  `getDeclaredField` 会解析字段类型并用**声明类的 CL** 加载它，引用类型会让生成类的链接
  依赖平台可见性。int 的描述符 `I` 不引用任何类。
- `selfCheck()` 已改为**只生成并定义类、不构造方块**：一个"检查是否可用"的方法
  绝不能有副作用（构造方块会毒化注册表），也必须与注册窗口开关无关
  （游戏启动后窗口必然关闭，绑定层完全正常时自检却报"窗口已关闭"比不检查更糟）。

## 修复两个静默失效根因（Mod 加载链路）

### 根因 1：契约入口从未接上
`LoaderMain.invokeModEntrypoints()` 用 runtime 的具体类 `ModContext` 传参，
并用 `getMethod("initialize", runtime.ModContext.class)` 找方法；
而 Mod 按契约声明 `initialize(org.loader.api.ModContext)`。
`Class.getMethod` 按精确类型匹配 → 必然 `NoSuchMethodException` → 每个 Mod 都加载失败，
且错误消息写「缺少标准入口」，把矛头指向 Mod 作者。

修法：新建 `ApiModContext implements org.loader.api.ModContext` 契约 facade
（契约 Javadoc 自述就是这个设计：delegates to internal runtime impl）；
`LoaderMain` 先 `isAssignableFrom` 检查再实例化，避免 ClassCastException。

### 根因 2：注册链在生产路径是死代码
`MinecraftBootstrap` / `EntryPointHook` 从不调`BootstrapGate.ensureBootstrapped()`，
`RegistrationPhase` 整链只有测试在调 → Mod 声明的方块永不落地，且无任何报错。

修法：`EntryPointHook.invokeMinecraftMain` 在 `beginMinecraftBootstrap()` 之后、
调游戏 main 之前插入 `runModRegistrations()`；失败必炸（继续启动 = 玩家看到
「少了东西但没报错」的游戏，排查线索已随启动日志滚走）。

### `defer`的「永不失败」设计是致命漏洞
`runRegistrations` 只在 `ensureBootstrapped()` 内调一次，bootstrap 后登记的动作
永远不被执行也无提示。ABI 契约早有明文 `@throws IllegalStateException 注册时机已过`。
修法：`windowClosed` 时 `defer` 抛异常——**契约写了而实现不响，是最糟的一种脱节**。

### ApiMinecraftRegistry 两个真实缺陷
- 构造函数调`detectItemBinding()` → 创建注册表视图这个纯内存动作强依赖Minecraft 类，
  无游戏 CL 时炸。改惰性探测（`volatile Boolean itemBindingAvailable`，首次 `item()` 才探测）。
- `findBlock` 把「补numericId」这个可选增强当必需，游戏类不可用时整个只读查询抛异常。
  改`try/catch RuntimeException` 容错降级，返回原句柄。

## 测试基础设施的关键洞察

### 本轮修的最后3 项失败（都是真实生产缺陷）

**1. OVERWRITE 冲突规则是死代码（ConflictLedger）**
`exclusiveKey` 把 `point` 拼进键 → `MODIFY_ARG|…#0` 与 `OVERWRITE|…#0`
落进不同桶 → `detect()` 从未被调用 → 「OVERWRITE 丢弃方法体」这条
精心写好的规则一次都没执行过。
根因是**粒度不匹配**：OVERWRITE 是方法级声明，ordinal 是指令级的。
改为按目标方法索引 + `mutuallyExclusive` 语义判定。

**2. dryRun 在空白账本上预演**
`new ConflictLedger()` 只能检出同一批声明之间的冲突，
对「与已装 Mod 冲突」这个主要用途完全无效。
改为在自身状态的副本上预演（Claim 是不可变 record，可安全共享）。

**3. 带参回调不压栈（最严重）**
`pushCallback` 无条件发`INVOKESTATIC <desc>`，**从不为参数压栈**。
ABI 允许 `onTick(InjectionContext ctx)` → 任何用InjectionContext 的 Mod
都得到栈下溢字节码。
症状极具欺骗性：`AnalyzerException: Error at instruction 0:
Cannot pop operand off an empty stack` —— 指令 0 就是那条正常的回调调用。
修复：新增 `InjectionContextFactory`（runtime侧），
生成 `LDC owner → LDC methodName → forMethod → callback`。
未知参数类型显式报错，不塞默认值（塞 0/null 会让Mod 基于错误数据决策）。

## 端到端加载打通 + ClassVisibility 真实契约漏洞修复

### 修 ClassVisibility：`org.loader.runtime.minecraft.` 曾错误地公开给 Mod

**根因**：该包（平台与 Minecraft 的绑定实现：反射、字节码生成、类查找）
被写在 `PUBLIC_RUNTIME_PACKAGES` 白名单里，于是 `BehaviourDispatch`、
`ReflectiveWorldView` 对 Mod 全部 `PARENT_FIRST` 可见。Mod 可以直接调
`BehaviourDispatch` 派发行为、注册生成方块，**绕开 ModContext 的全部
生命周期与合规检查**。

**改法**（修实现而非改契约）：
- 从 `PUBLIC_RUNTIME_PACKAGES` 移除 → 加入 `RUNTIME_INTERNALS`（判 FORBIDDEN）。
- 改前用 grep 核验过安全性：`mili-abi` 对 `org.loader.runtime` **零 import**
  （唯一命中是 Javadoc 提及），公开 Runtime 包（tick/mod/client/service）
  对 minecraft 包也是零签名依赖。Mod 拿到的是 ABI 的 `WorldView` 实例，
  接口方法由父 CL 完成方法解析，Mod 从不需要加载实现类 → 隐藏不构成回归。
- 验证：`:mili-loader:test` 全量 90 项 `BUILD SUCCESSFUL`，零回归。

**顺带修的第二个漏洞**：`org.loader.runtime.RuntimeEnvironment` 位于包根，
无 `.` 前缀可匹配 → 落进 `SELF_FIRST`。它是 `ModContext.environment()` 的
返回类型，Mod 写 `RuntimeEnvironment.CLIENT` 会先在自己 classpath 上失败一轮
再回退；若某 Mod jar 恰有同名类就**分裂成两份**，`==` 判定失效。
新增 `RUNTIME_ROOT_SPI` 名单显式放行（判据同 `KERNEL_SPI`：Mod 要用平台就
必须能解析该类型）。

### IT 测试的 3 项失败：2 项是自己写错，1 项暴露了上面的漏洞

### 教训（可复用）

- 断言跨 ClassLoader 的类时，**绝不能强转**成 app CL 里的同名类。
  正确做法是断言 `getClassLoader()` 身份 + 反射读字段。
- 断言「jar 里某文件的内容」必须走 `ZipFile.getEntry`，直接读 jar 字节流
  是压缩态，任何内容断言都是假绿。
- **类可见性白名单要逐条核验「该包是否出现在 ABI/公开 Runtime 的公开签名里」**，
  再决定放不放行。凭直觉加白名单会造出绕过封装的洞。
