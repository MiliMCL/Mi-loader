# 2026-10-05

## 修复 CI 反编译流水线从未真正执行 + 首次成功发布 v26.2

### 根因（三层，逐层暴露）
1. `test_client/` 在 .gitignore 中，Minecraft JAR 从未入库（仓库仅 400KB）。
   CI 的 `find . -path '*test_client*'` 永远找不到 → `found=false` →
   prepare/decompile/generate 全部 SKIPPED，且被 `onlyIf` 静默吞掉。
2. 由此 `minecraft.json` 从未被打进 JAR，`verifyPlatformJar` 报
   `META-INF/mili/minecraft.json missing`，release 在最后一步失败。
3. **关键坑**：`File(path).absoluteFile`（`resolveMinecraftArtifact` 与
   `minecraftArtifactSha256`）以 **Gradle daemon 的工作目录**
   （`~/.gradle/daemon/<ver>/`）为基准，而非项目目录。
   即使 JAR 已下载、`MINECRAFT_ARTIFACT=test_client/26.2.jar` 正确传入，
   仍解析成 `<daemon>/test_client/26.2.jar`（0 字节）→ 依旧 SKIP。
   这是"看起来都配对了却还是跳过"的真正原因。

### 改动（仅限构建报错与发布必要）
- ci.yml / release.yml：从 piston-meta 官方清单按 `minecraftVersion` 解析
  client 下载 URL，校验官方 SHA-1，导出**绝对路径** MINECRAFT_ARTIFACT。
  废弃原先探测仓库内 `test_client/` 的逻辑。
- mili-minecraft-integration：`resolveMinecraftArtifact` 相对路径锚定到
  projectDirectory；CFR `maxHeapSize = "4g"`（全量 MC 用默认堆会 OOM）。
- mili-loader：`minecraftArtifactSha256` 同样锚定项目目录；
  移除 skip-path 下失效的 `artifactSha256` 断言。

### 验证结果（v26.2 已发布）
- CI 三 job 全绿；真实反编译：10952 classes → 7055 sources →
  37 events / 10 registries（修复前全是 SKIPPED）。
- Release 产物 `mili-0.1.0-mc26.2.jar`（283,989 B，258 entries），
  SHA256SUMS 校验 OK，minecraft.json 指纹
  `40896ee9...290` 与官方 26.2 client.jar 完全一致。

### 重要结论：发布物是"加载器"，不含 Minecraft 本体
- JAR 内 `net/minecraft` 条目 = **0**，`org/loader` = 249，`.java` = 0。
- 这是 ADR 0005「Minecraft Is Host, Not Kernel」的设计刻意选择，
  也规避 Mojang 再分发条款；反编译源码仅作构建期元数据输入。
- 要真正"启动完整 Minecraft"，需 loader + 用户自备正版 MC 安装，
  由 `MinecraftDiscovery` 发现后以 URLClassLoader 同进程加载
  （入口 `net.minecraft.client.main.Main`）。
- 目前仓库无 distribution/application 插件，README 提到的 distTar/distZip
  与实际不符——如需开箱即用分发包需另行实现（本次未改，超出授权范围）。

## 新增 mili-installer + distribution 打包（第二轮，全做完）

### 动机
发布页 JAR 仅 285KB / `net/minecraft` 条目为 0 —— 是纯加载器，不是游戏。
用户要求「下载发布页即可启动完整 Minecraft」。README 早已宣传
distTar/distZip/bin/mili-loader，但构建脚本里从未实现。

### 关键决策：不把 MC 合并进 jar
合并 MC 类违反 Mojang EULA，且合并了 39MB client.jar 仍缺 88MB libraries
与 480MB assets，照样跑不起来。改为：发布加载器 + 安装器，首次运行从
Mojang 官方 CDN 拉取并逐个校验 SHA-1。分发包维持 KB 级。

### mili-installer（零第三方依赖，仅 JDK）
- `Json` — 手写 RFC 8259 解析器（用户可能只有 JRE，不能引入 Gson）
- `MojangMetaClient` — manifest → version JSON，不碰任何认证端点
- `VerifiedDownloader` — 流式 + SHA-1 + `.part` 原子 rename + 幂等跳过
- `PlatformRules` — 运行时求值 77 个带 rules 的 libraries 与 natives classifier
- `LibraryInstaller` — 标准 Maven 布局 + natives 解压到 `natives/<os>/`
- `AssetInstaller` — 虚拟资源树，8 线程，约 480MB
- `InstallOrchestrator` / `InstallerMain` — 幂等 CLI

### 踩过的坑（重要）
1. **Mojang 元数据类型不一致**：真实 26.2 的
   `javaVersion.majorVersion` 是**数字 25.0**，旧清单是字符串 `"25"`。
   用 `Json.str` 读会得 null → 回退 "8" → 提示「26.2 建议使用 Java 8」。
   新增 `Json.strOrNumber` 同时兼容两种编码。
2. **Kotlin DSL 打包布局**：`into("README.txt")` 会让 Gradle 把它当**目录**，
   产出 `README.txt/README.txt`；裸 `into("mods")` 后紧跟 `from(...)` 会让
   后续 from 落到兄弟层级。正确写法：`into(root){ into("core"){from(..)}; from(file) }`。
3. **断言位置**：布局断言只放在 ci.yml 时，release job 照样发出坏包。
   现在 release.yml 也断言，并在 publish 前执行。
4. **本机限制**：用户 8G 内存，禁跑 java/gradle（会卡机）。但
   `javac` 单文件 + 反射 MiniRunner 可用于快速验证；`./gradlew distTar
   --offline` 也只需 43s，可用来验证打包布局（已获用户默许此次使用）。

### Mojang rules 语义（曾写错断言）
顺序扫描，首个匹配决定，**无匹配则默认 allow** —— 所以「disallow 写外平台」
根本不生效，排除必须靠匹配本机的 rule。

### 验证结果
- CI 4 个 job 全绿；42 个 installer 单测通过。
- smoke test 真实连上 Mojang：131 个库、client 37.4MiB、assets 458MB。
- 发布页 v26.2 现有 4 个资产，SHA256SUMS 全 OK；tar.gz 布局正确，
  installer 28 个类已合入平台 JAR，MC 指纹与官方一致。
