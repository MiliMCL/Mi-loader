## 修复 mili-loader.bat 在 Windows cmd 下的解析崩溃

**现象**：用户在 `D:\mili-0.1.0-mc26.2 (1)\mili-0.1.0-mc26.2\bin` 执行 `mili-loader.bat` 报四条错：
```
'浠?Mojang' 不是内部或外部命令
'local' 不是内部或外部命令
批处理参数替换中的路径运算符的下列用法无效: %~fI"
命令语法不正确。
```

**根因（经 2×2 对照实验 + 二分定位确认）**：
1. 主因：文件是 **UTF-8 中文 + LF 行尾**。cmd.exe 在 OEM 代码页（zh-CN 为 GBK/936）下按 CRLF 切分命令，LF-only 文件退化为按字节猜边界，把单行劈成碎片 → `setlocal` 的 `set` 被吞只剩 `local`；`%%~fI` 首 `%` 丢失报 `%~fI"` 无效。
2. 附带坑：**REM 注释行内的字面 `%` 也会被 cmd 展开**并破坏解析（我自己第一版修复注释里写了 `"%~fI"` 就再次触发，二分定位到第 12 行才发现）。
3. 中文不是必要条件——纯 ASCII + LF 遇到 `%` 展开同样会崩。中文只是让错误信息更难看。

**修复**：
- `mili-loader/distribution/bin/mili-loader.bat` → 改为纯 ASCII（英文注释）+ CRLF，注释中不出现字面 `%`
- `D:/mili-0.1.0-mc26.2 (1)/.../bin/mili-loader.bat` → 同步上述干净版本
- 新增 `.gitattributes`：`.bat`/`.cmd` 强制 `eol=crlf`，防止 `core.autocrlf` 检出时打回 LF
- `mili-loader/build.gradle.kts` 新增 `launcherScriptCheck` 任务（挂到 `check`/`build`），校验三条：无 BOM、纯 ASCII、全 CRLF 无裸 LF、REM 行无 `%`

**验证**：chcp 936/65001/437 三种代码页下零报错，参数透传正常，含空格与括号的路径解析正确。全程用 echo stub 掉 java，未启动 JVM（遵守用户"不在本机跑 Java"约束）。

**遗留**：D 盘旧版曾硬编码 `--gameDir "E:\mili-0.1.0-mc26.2\game"`（指向不存在的旧路径）、伪造 `--accessToken`、`${clientid}` 未展开；同步后这些参数已移除，回到干净模板形态。

**工具坑**：Write 工具在 Windows 上写出的文本文件是 **LF 行尾**，写 .bat 必须用 Python 显式 `.replace('\n','\r\n')` + `.encode('ascii')` 写二进制。

## 修复启动崩溃：SharedConstants ClassNotFoundException + 零Mod 静默失效

**现象**：`[Mili] ClassLoader 拓扑:` 打印后立即
`IllegalStateException: Mod registration failed` →
`ClassNotFoundException: net.minecraft.SharedConstants`，
并伴随 `0 registration(s) were queued by mods in their initialize() methods`。

**根因 1：生产路径从未调用 `Reflect.useGameClassLoader(...)`**
`Reflect.gameClassLoader()` 回落到 `Reflect.class.getClassLoader()`（平台 AppClassLoader），
而 Minecraft 类只存在于 `MinecraftClassLoader` 的 URL 里 → 平台 CL 看不见 `net.minecraft.*`。
**为什么测试全绿**：`GameTestClassLoader.install()` 调了它，所以「有 MC 的测试」永远看不到这个缺陷 ——
测试与生产的唯一区别就是这一行。

**根因 2：Mod 目录与 gameDir 不是同一个目录**
分发包布局是 `<dist>/{bin,core,mods,game}`：Mod 在 `<dist>/mods`，Minecraft 在 `<dist>/game`。
启动脚本传 `game/` 作 gameDir（正确），但平台按 `gameDir.resolve("mods")` 找 Mod → 扫到不存在的 `game/mods/`。
`ModDiscovery` 不抛异常只返回空列表 → **静默失效**：游戏正常启动、Mod 内容全空白、日志无任何线索。

**修复**：
- `Reflect.java`：`ThreadLocal<ClassLoader> GAME_CL` → `static volatile`。ThreadLocal 在此不仅无益（静态字段本就按定义它的 CL 隔离），还会让 `minecraft-main` 线程看不到主线程设的值 → 游戏运行期反射全部回落。
- `MinecraftGameProvider.createGameClassLoader()`：创建 MC CL 后立刻 `Reflect.useGameClassLoader(gameCL)`，必须在任何 Mod 加载/注册排队之前。
- `LoaderConfig.at(gameDir, modsDir)` 重载 + `LoaderMain.parseArgs()` 拆平台参数与 MC 参数。
  关键：MC 用 joptsimple，遇到不认识的 `--xxx` 直接 `UnrecognizedOptionException` 拒绝启动，平台选项必须在转发前摘掉。
- `ModClassLoader` / `ModClassLoaderManager`：新增显式 `modsDir` 构造参数；旧签名保留委托（`gameDir.resolve("mods")`），避免破坏 ~30 处测试调用点。
- `LoaderMain.reportDiscovery()`：打印 `[Mili] Mod 目录: ... (JAR/ZIP=n, 识别=m)`，`n>0 && m==0` 时报警。
- 两个启动脚本补 `--mili-mods "%MODS_DIR%"`；README 补该参数与两条故障排查。

**新增回归测试**：
- `DistributionModsDirTest`（loader）：分发包平级布局能发现 Mod，且断言 ModClassLoader **真的把 JAR 挂进了 classpath**（只看「能发现」不够，挂了才等于游戏能加载）。
- `ReflectGameClassLoaderVisibilityTest`：另起线程断言 `gameClassLoader()` 可见 —— 直接锁死 ThreadLocal 那个坑。不依赖 Minecraft，用替身 CL 即可。

**遵守约束**：用户机器 8G 内存、禁止本机跑 Java 进程，本次只做静态核对，编译与测试交由 CI（`compileJava compileTestJava` + `test` + `distTar`，均已覆盖这两个模块）。

结果：`Build & Test (Java 25)` 在 CI 上**通过**，说明上一轮的运行时修复（Reflect 全局可见性 + mods 目录）有效。

## 修 CI 构建：三个 Gradle 9.7.1 陷阱（本机不跑 Java，全部靠 CI 暴露）

### 坑1：`ByteArray.windowed(2)` 不存在 → 脚本编译期失败，**所有** Gradle 任务全挂

`windowed()` 是 `kotlin.text` 的 **CharSequence** 扩展函数，`ByteArray` 上没有。
Kotlin DSL 脚本在**配置期**编译，脚本编译失败会让 `compileJava`、
`verifyMinecraftArtifact`、`test`、`distTar` 全部无法启动 —— 报错点很远（都在 442 行），但影响面是整个构建。
改法：直接按下标遍历字节数组统计 CRLF / 裸LF，不依赖任何集合扩展。

### 坑 2：`apply(from = ...)` 在 Gradle 9 已移除 → **任务静默消失**

边界校验原本住在 `distribution-boundary.gradle.kts`，靠 `apply(from=...)` 引入。
Gradle 9 遇到它**静默忽略**——不报错、不警告，脚本根本不执行，于是
`:mili-loader:distributionBoundaryCheck` 任务从未注册，CI 报：

```
Cannot locate tasks that match ':mili-loader:distributionBoundaryCheck'
as task 'distributionBoundaryCheck' not found in project ':mili-loader'.
```

**这个坑最阴险的地方**：本地用旧 Gradle 时 apply 仍有效、校验照常跑，完全看不出来；
只有 CI 升级到 Gradle 9 才现形，而失败表现是「任务消失」，极易被误判成 CI 配置写错。
Gradle 9 里脚本级组合要走 `plugins {}`，预编译脚本插件需要 `buildSrc` —— 为一个校验任务引入
buildSrc 不划算，**内联进主构建脚本**最诚实。原`distribution-boundary.gradle.kts`
保留为设计文档，并在文件头顶部加显著警示「本文件已不再被加载，请勿在此改规则」。

### 坑 3（我自己犯的）：Kotlin 脚本里不能用 `java.util.zip.ZipFile` 全限定名

内联时顺手写成 `java.util.zip.ZipFile(fatJar)`，报 `Unresolved reference 'util'`。
**`.gradle.kts` 是编译成类的脚本，只能解析 `import` 进来的符号** —— Kotlin 不支持
Java 那种「包名前缀即引用」的全限定解析（`kotlin.*` 除外）。
改用第 15 行已 import 的 `ZipFile` 即可。

### 附带：`by tasks.registering` 在 Gradle 9.6 已废弃

改成 `val x = tasks.register("name") { ... }`。
注意**不要**用 `by tasks.register("name")` —— 那个委托的 `getValue` 同样已废弃。

### 工具坑：git push 在本机会挂死

`git push` 反复 SIGTERM/无响应（3 分钟无输出）。根因是全局配了
`credential.helper = git-credential-wincred.exe`（Windows 凭据管理器），
在沙箱环境里弹不出 GUI 提示就永久阻塞。绕过：

```bash
GIT_TERMINAL_PROMPT=0 git -c credential.helper= -c http.version=HTTP/1.1 \
  push "https://x-access-token:<TOKEN>@github.com/<owner>/<repo>.git" HEAD:refs/heads/<branch>
```

顺带发现：`git push origin 26.2` 会报 `src refspec 26.2 matches more than one`
（分支名与 tag 同名 `26.2`），必须写完整 refspec `HEAD:refs/heads/26.2`。

### 教训

连续三轮 CI 才收敛，且**后两轮的错误都是我自己上一轮引入的**。
在没有本地 Java 环境的前提下改`.gradle.kts`，等于盲改编译型 DSL ——
每轮只能改一处、推一轮、看一轮反馈。正确做法是先通读整个脚本文件、
把所有可疑 API 一次性找齐（`windowed` / `apply(from)` / 全限定名 / 废弃委托），
再一次性推送。

**最终结果**：run `37399974950`（HEAD=`d678fe2`）**6 个 job 全绿**：
Mincraft 26.2 Pipeline / Module Boundary Validation / Version Single Source of Truth /
Build & Test (Java 25) / Installer smoke test / Distribution Boundary (No Minecraft)。
边界检查日志确认真的执行了（扫描平台 JAR 576 个条目 + 分发目录），
Gradle 实现与 CI 的独立 shell 实现**同时**通过—— 两套独立实现互不复用的设计生效了。

## 分发包实测：资源全丢 + 零Mod 加载（根因定位与修复）

**实测环境**：`D:\mili-0.1.0-mc26.2 (1)\mili-0.1.0-mc26.2`，`latest.log` 2135 行，游戏能进能玩，但界面无背景图、无多语言、Mod 完全不加载。

**根因 A：从未向 Minecraft 传 `--gameDir`（资源全丢的真正原因）**
`args[0]` 只被平台消费，Minecraft 自己收不到；MC 拿不到 `--gameDir` 时**把当前工作目录当游戏目录**，而脚本是在 `bin/` 里执行 java 的，于是 gameDir 变成 `bin/`：
- 日志首行 `Can't open the resource index file: .\assets\indexes\32.json` —— 相对路径 `.\` 暴露了真实 gameDir
- 资源其实在 `game/assets/indexes/32.json`（586KB，完整），`bin/assets/` 只有 `skins/`
- 索引读不到 → **背景图 + lang(多语言) + 全部音效**一起消失（三者同源，不是三个 bug）
- `icons/icon_16x16.png` FileNotFound、`options.txt`/`saves`/`resourcepacks` 全落在 `bin/` 而非 `game/`
- 反证：`bin/` 下存在本该在 `game/` 的 `options.txt`、`saves/`、`resourcepacks/`、`usercache.json`

**关键认知**：Minecraft 的资源与存档目录按 `--gameDir` 推导，**不是按「jar 在哪」**。平台定位 jar 用 gameDir、交给游戏用 `--gameDir`，两者必须一致，否则平台能找到游戏、游戏却在自己目录里找资源。

**根因 B：分发包 JAR 陈旧，`--mili-mods` 支持根本不在里面**
`core/mili-0.1.0-mc26.2.jar`（09:11）里的 `LoaderMain.class` 仍是**旧版**：
- 有旧方法名 `createModClassLoader` / `getModClassLoader` / `shutdownMods`（当前源码已无）
- 无 `parseArgs` / `reportDiscovery` / `--mili-mods` / `LoaderConfig.at(Path,Path)`
→ 即上一轮修的 Mod 目录问题**根本没进包**。两个脚本已传 `--mili-mods`，但**必须重新构建 JAR 才生效**；反之旧 JAR 收到该参数会当 MC 参数转发 → joptsimple `UnrecognizedOptionException`。

**修复**：
- `LoaderMain.parseArgs()`：解析出 `resolvedGameDir` 后，若调用方未指定 `--gameDir` 则注入 `--gameDir <abs>`（幂等，不重复注入）；`parseArgs` 降为包级可见便于测试
- `LoaderMain.reportDiscovery()`：Mod 目录不存在时明确报警（此前只在 `jarCount>0 && mods.isEmpty()` 时告警，目录缺失是完全静默的）
- 两个启动脚本补 `--mili-mods`（bin/*.bat 与 bin/mili-loader）
- 新增 `LaunchArgPassthroughTest`（5 个用例）：锁死 `--gameDir` 注入、`--mili-mods` 生效、平台参数必须从 MC 参数里摘掉（否则 joptsimple 拒绝启动）

**附带发现（未修，需决策）**：`mods/stardewvalley.jar` 只有 18 个条目、**0 个 assets**（源码 `Stardewvalley_mod-main/main/resources/assets/` 有完整 blockstates/lang/textures，但打包时没进去）；且平台侧无任何 ResourcePack/资源包注入实现（`mili-minecraft-integration` 无相关代码）→ Mod 自带资源目前无法进入游戏。入口类已正确 `implements org.loader.api.Mod` + `initialize(ModContext)`，mod.json 三元组 0.1.0/1/26.2 与 platform.json 一致，**加载契约本身没问题**。

**工具坑**：`Write` 工具写 .bat 会产生 LF 行尾且可能带入非 ASCII；改 .bat 后必须用 Python 复核 BOM/非 ASCII/裸LF/REM 行 `%` 四项（对齐 `launcherScriptCheck` 规则）。

**遵守约束**：全程未启动 JVM，编译与测试仍交 CI。

## 实现物品注册 + 修复 ExceptionInInitializerError 崩溃

### 里程碑：Mod 端到端跑通
用户实测日志确认上一轮 JAR 修复完全生效：
```
[Mili] Mod 目录: D://mili-0.1.0-mc26.2//mods  (JAR/ZIP=1, 识别=1)
[Mili]   发现 Mod: stardewvalley v3.1.6-mili
[Mili] Mod initialized: stardewvalley -> stardewvalley.modid.StardewValley
```
`Completely ignored arguments` 消失 → `--mili-mods` 被正确剥离。
随后撞上 `ApiMinecraftRegistry.item()` 的 `UnsupportedOperationException`
（源码里明写"not implemented yet"）——即上一轮排查出的第三个问题。

### 新增 ItemRegistrar（物品注册端到端）
`mili-minecraft-integration/.../item/ItemRegistrar.java`，照BlockRegistrar 模式。
**从反编译产物查证的真实 26.2 API（不要凭记忆写）**：
- `Item(Properties)` 单参构造（不是老版的 Item)/`Item.Properties.setId(ResourceKey<Item>)` —— **必须先 setId 再 new**，
  因为构造器里调 `properties.itemIdOrThrow()`，会把组件初始化器挂到
  `BuiltInRegistries.DATA_COMPONENT_INITIALIZERS`，id 为空直接抛
- 堆叠数是 `stacksTo(int)`、耐久是 `durability(int)`（旧版才是 maxStackSize/maxDamage）
  → 实现里**两个候选名都探测**，都不存在只记日志不抛异常
- `Registries.ITEM` / `BuiltInRegistries.ITEM` 存在；后者是 `DefaultedRegistry`
  且 `registerDefaultedWithIntrusiveHolders`，但 `Registry.register` 静态方法内部
  会正确走 intrusive 分支，**不需要**手工构造 Holder
- `Registry.register(Registry,ResourceKey,Object)` 必须在**接口** `Registry.class` 上找
  （用 DefaultedMappedRegistry 会NoSuchMethodException）—— 与方块同一个坑
- `blockItem()` 有值时注册为 `BlockItem(block, props)`，否则放不出方块
- `ApiMinecraftRegistry.item()` 改为与 block() 同构：建句柄 + `RegistrationPhase.defer`

**修掉一个自造 bug**：`resourceKey()` 原用「取类名最后一段当字段名」推导，
而 `Registries` 的字段是 ITEM/BLOCK，与类名不同 → 必然 NoSuchFieldException。
改为**显式传字段名**，并删掉 `ownerField()`。

### 崩溃根因：catch (RuntimeException) 拦不住 Error
用户实测崩溃栈：
```
Mod.initialize → StardewValley.reportContent → registry.findBlock
  → BlockRegistrar.numericIdOf → BuiltInRegistries.BLOCK
  → ExceptionInInitializerError
Caused by: IllegalArgumentException: Not bootstrapped (called from registry minecraft:game_event)
  at Bootstrap.checkBootstrapCalled → BuiltInRegistries.<clinit>
```
**`ExceptionInInitializerError` 继承 `LinkageError` → `Error`，不是 RuntimeException**，
所以 `ApiMinecraftRegistry.findBlock` 里的 `catch (RuntimeException notQueryableYet)`
形同虚设 —— 一个**纯只读查询**把整个 Mod 初始化炸掉了。
修法：`catch (RuntimeException | Error)`，三处（findBlock / findItem /
BlockRegistrar.numericIdOf / ItemRegistrar.numericIdOf / lookupBlock）统一加固。
**语义依据**：契约问的是「注册了吗」，答案已确定为「注册了」；游戏侧还答不了时
返回 numericId=-1 的句柄即可，不该致命。

**解法**：`-Dorg.gradle.unsafe.incremental=false`（每次全量重编该模块，慢约 1 分钟）
+ 失败后删掉 `build/tmp/compileJava/compileTransaction` 残留目录。已固化进 rebuild-platform.sh。

## 修复 BuiltInRegistries 类毒化（NoClassDefFoundError）

### 事故：Mod 初始化成功了，平台开窗却拒绝启动
用户实测（换了上轮JAR 后）：
```
[INFO] Verified 3 blocks + 3 items are in the registry
[INFO] stardewvalley. Ready. 3 crops, 3 seed items.   ← Mod 侧全部成功
[Mili] Mod initialized: stardewvalley -> stardewvalley.modid.StardewValley
ClassLoader 拓扑: stardewvalley sources=1 loaded=39
Exception in thread "main" IllegalStateException: Mod registration failed;
  refusing to start Minecraft without it. 6 registration(s) were queued...
Caused by: NoClassDefFoundError: Could not initialize class BuiltInRegistries
  at Reflect.staticField → RegistrationPhase.openRegistryWindow(220)
  at BootstrapGate.ensureBootstrapped(53)
Caused by: ExceptionInInitializerError: IllegalArgumentException: Not bootstrapped
  at BuiltInRegistries.<clinit>(184)          ← 毒化的源头在更早
```

### 根因：JVM 类初始化失败【不可重试】
关键机制：`BuiltInRegistries.<clinit>` 要求 `Bootstrap.isBootstrapped==true`。
若在置位前有人先碰到该类 → 抛 "Not bootstrapped" → **JVM 把该类永久标记为
Erroneous，此后任何访问都直接 NoClassDefFoundError，不会重试 <clinit>**。

上一轮的错误修法：`catch (RuntimeException | Error)` 让 Mod 的只读查询不再炸，
**但代价是把失败推迟了** —— 毒化已经发生，无法回滚。
"catch住症状"不等于"修好"：真正的修复必须是**避免首次失败**。

事故链：
`Mod.initialize() → findBlock()（纯只读意图）→ 首次触碰 → 毒化`
→ Mod 因异常被 catch 而"成功"跑完 → 平台 openRegistryWindow 再碰 → NoClassDefFoundError
→ 报"refusing to start Minecraft without it"，错误完全指不到「某个Mod 早先查了一下」。

### 修复：固化「先置标志、后触碰」的唯一安全顺序
- `RegistrationPhase.ensureRegistriesReadable()`（新增 public static，幂等）：
  内部复用 `openRegistryWindow()`，即"置 Bootstrap.isBootstrapped → 再触碰注册表类"。
- 所有触碰点改为先经由它：
  `BlockRegistrar.blockRegistry()` / `BlockRegistrar.blockKey()`（读 Registries.BLOCK）
  `ItemRegistrar.itemRegistry()` / `lookupBlock()` / `resourceKey()`（读 Registries.ITEM/BLOCK）
  `ReflectiveWorldView` 两处（Mod 可达的世界查询，同样会毒化）
  `RegistrationPhase.drainUnregisteredBlocks()`（幂等二次保险）
- **注意**：`Registries` 与 `BuiltInRegistries` 是两个独立类，各自 <clinit> 失败都不可重试，
  读 `Registries.BLOCK/ITEM` 同样要先保护（这点是测试帮我发现的，初始漏了）。

### 新增回归测试（已验证非假绿）
`RegistryClassInitOrderTest`（6 用例，全绿）—— 静态扫描源码：任何
`Reflect.staticField(...)` 触碰注册表的位置都必须在 8 行窗口内先调
`ensureRegistriesReadable()`，且 `openRegistryWindow` 内必须「置位在前、触碰在后」。
**有效性验证**：临时移除 `itemRegistry()` 的保护调用后，该用例立刻 FAILED；
恢复后全绿。另修正了测试自身的一个误报（保护调用与触碰点之间夹注释，
只回看 1 行会误判，窗口放宽到 8 行）。

### 交付
`dist-out/mili-0.1.0-mc26.2.jar`，978,613 字节，
sha256 `720b305bf0123dfb015a06116a86b8eaaf1602ba93599ca840e7fed0d0227866`。
已确认 4 个类字节码里都含 `ensureRegistriesReadable`。

### 教训（值得记住）
JVM 类初始化失败是**不可逆**的。对这类"提前触碰游戏类"的防护，
正确做法不是把异常 catch 住，而是**保证首次触碰就是安全的**。
catch 只应作为最后一道保险，不能当成主要手段。

**新增 `ModResourcePacks`**（走游戏原生资源包抽象，资源随 jar 走）：
- `RepositorySource` → `Pack` → `PackResources` 链，全部动态代理
- **26.2 真实结构（从 test_client/26.2.jar 字节码逐条读出，未凭记忆）**：
  - `Pack.ResourcesSupplier` 是 **Pack 的嵌套接口**（不是顶层类！），
    方法 `openPrimary(PackLocationInfo)` / `openFull(PackLocationInfo, Metadata)`

这与 `runModRegistrations()` 的策略刻意不同（那里失败= 内容缺失，必须炸）。

**接线**：`EntryPointHook.scheduleResourceInjection()` 遍历 `mgr.all()` 拿 Mod JAR。

4. `catch (RuntimeException)` 漏掉 `ReflectiveOperationException`（受检异常）

## PlatformLog 生效后定位到三个真实根因（全部已修）

### 根因 1：Builder.type() 是 protected，getMethod 拿不到
```
NoSuchMethodException: CreativeModeTab$Builder.type(CreativeModeTab$Type)
```
反编译源码第 187 行：`protected Builder type(Type type)`。
**`Class.getMethod()` 只返回 public 方法** —— 这是本项目第一次（也是最隐蔽的）
撞上"方法存在但取不到"。
字节码里能看到 `type` 符号、源码 grep 却搜不到 `public Builder type`，
两个信号矛盾时以"访问修饰符"解释。
**修法**：不调它 —— 默认值已是 `Type.CATEGORY`，正是想要的。
另加 `setTabTypeIfNeeded()`：用 `getDeclaredField("type")` 读当前值，
只在不是 CATEGORY 时才用 `getDeclaredMethod + setAccessible` 设置。
（防御性读取：默认值改了也不至于没标签）

### 根因 2：资源注入在 Minecraft 构造完成前执行
```
BridgeMismatchException: Cannot reach Minecraft.resourcePackRepository
```
**不是字段名错**（已核实第 352 行确实是 `resourcePackRepository`）。
真正原因：`Minecraft.getInstance()` 返回静态字段 `instance`，
它在构造**一开始**就被赋值，但 `resourcePackRepository` 这些 final 字段
要到构造中后段才赋值 → 拿到的是"实例存在但字段仍 null"的半成品。
时间线佐证：注入发生在 13:34:00，而 `Reloading ResourceManager` 在 13:34:02，**早了 2 秒**。

**修法**：就绪判据从"实例非 null"改为"**resourcePackRepository 字段已赋值**"
（`clientFullyConstructed()` 反射读该字段，非 null 才算就绪）。
判据选这个字段有理由：它是 final 且在资源管理器构建那段初始化，
一旦非 null 就说明正好走到了能安全注入的时机。

### 根因 3：我上轮加的"保险"本身成了 bug
```
BridgeMismatchException: The registration window is already closed
  at RegistrationPhase.openRegistryWindow(187)
  at RegistrationPhase.ensureRegistriesReadable(260)
  at RegistrationPhase.drainUnregisteredBlocks(335)
  at RegistrationPhase.closeRegistryWindow(283)
```
`drainUnregisteredBlocks()` 由 `closeRegistryWindow()` 在**窗口已关闭之后**调用，
而我上轮在它开头加了 `ensureRegistriesReadable()`（内部走 openRegistryWindow）
→ 每次关窗必然抛错，**且屏蔽掉了本方法真正要报告的内容**（未注册的方块）。

**教训**：加"防御性调用"前必须确认它在**所有**调用路径上语义都成立。
这里是**我自己的预防措施制造了故障**，比不写更糟。

1. **反射取不到 ≠ 方法不存在** —— 先查访问修饰符（protected/private 要用

## 三个反射细节错误（全部是"猜"造成的）

上一轮把 type() 修掉后，日志立刻暴露出三个新错误 —— 都是**反射层面的细节**，
不是设计问题。这轮的共同教训：**我一直在凭印象写字段/方法，而不是先查**。

### 根因 1：PackRepository.sources 是 Set 不是 List
```
BridgeMismatchException: PackRepository has no 'sources' field.
```
反编译源码第 36 行：`private final Set<RepositorySource> sources;`
我的 `findSourcesField()` 条件是 `List.class.isAssignableFrom(...)`
→ 不匹配 → 返回 null → 报"没有 sources 字段"。
**把"类型不匹配"说成了"字段不存在"**，这种错误信息会把人带偏很远。

**修法**：同时接受 List 与 Set；并新增 `describeFields()` 把真实字段
（名 + 类型）打进异常信息 —— 让下一次这类错误能被一眼看穿。

### 根因 2：lambda 传给 Supplier<ItemStack> 报 argument type mismatch
```
IllegalArgumentException: argument type mismatch
  at ModCreativeTabs.buildTab(ModCreativeTabs.java:127)   ← icon(...)
```
我传的是 `Supplier<Object>` lambda，而形参声明是 `Supplier<ItemStack>`。
泛型擦除后两者运行时都是 `java.util.function.Supplier`，
但 javac 按**声明类型**检查，lambda 生成类的类型不匹配 → 抛 IAE。

**修法**：改用 `Proxy.newProxyInstance` 生成实现游戏侧 `Supplier` 的类，
擦除后类型天然一致。理由写在代码注释里，也与项目内
`BlockPropertiesBuilder.lightLevel(ToIntFunction)` 的既有做法一致。

**这是一类通用陷阱**：任何 `Supplier<T>` / `Function<T,R>` 形参，
传 lambda 都有泛型声明类型不匹配的风险，需要 Proxy。

### 根因 3：getDeclaredField 不查父类
```
NoSuchFieldException: unregisteredIntrusiveHolders
```
字段名**完全正确**（MappedRegistry 第 66 行有声明），
但 `BuiltInRegistries.BLOCK` 的运行时类是 `DefaultedMappedRegistry`，
而字段声明在**父类** `MappedRegistry` 上。
`Class.getDeclaredField` 只看类自身，不含父类。

**修法**：新增 `findFieldInHierarchy()` 沿 superclass 链查找。
同样把"字段在父类"误报成了"字段改名了"（原日志文案就是
"field renamed?"）—— 又是错误信息误导。

### 值得记住的三条（本项目已反复踩）
1. **反射前先查确切的类型与声明位置**。字段类型（List/Set）、
   声明类（自身/父类）都要确认，不能凭印象。
2. **错误信息要能自证**。`describeFields()` 这类"把真实结构打印出来"的
   手段，值得成为反射失败时的标配 —— 否则排查全靠猜。
3. **泛型形参用 Proxy 而非 lambda**（Supplier<T>/Function<T,R> 等）。

## 不可变集合 + 第二个泛型 lambda（两处同类问题）

进展：`drainUnregisteredBlocks` 的 NoSuchFieldException **消失了**
（沿继承链查找生效），说明上轮第3 处修复正确。剩下两个新错误。

### 根因 1：PackRepository.sources 是 Guava ImmutableSet
```
java.lang.UnsupportedOperationException
  at com.google.common.collect.ImmutableCollection.add(ImmutableCollection.java:267)
  at ModResourcePacks.addRepositorySource(ModResourcePacks.java:193)
```
上一版把字段类型从 List 放宽到 Set 就以为完事了 —— 但**没看它是怎么构造的**。
26.2 构造器：
```java
this.sources = ImmutableSet.copyOf((Object[]) sources);
```
`add()` 在 ImmutableCollection 里就是直接 throw，**而且字段是 final**，
连"就地改内容"都不行。

**修法**：造一个「原有全部 + 新的」`LinkedHashSet`，
再用 `Field.set` **整体替换** final 字段。
final 只约束正常赋值，反射写入仍生效 —— 这是此路可行的根本原因。
比与不可变集合较劲、或者去找未公开写入口都干净。

**教训**：放宽类型判断只是"从一种错换成另一种错"。
判断一个集合能不能改，必须看**它怎么被构造的**，而不只是它是什么类型。

### 根因 2：displayItems 的 lambda 与 icon 完全同构
```
IllegalArgumentException: argument type mismatch
  at ModCreativeTabs.buildTab(ModCreativeTabs.java:145)
```
上一版只把 `icon` 改成Proxy，`displayItems` 仍在传
`BiConsumer<Object,Object>` lambda给`DisplayItemsGenerator`（双参函数式接口）
→ 同样的声明类型不匹配。
**同一个坑，同一处代码，两个参数** —— 说明修的时候没有成对处理。

**修法**：`newDisplayItemsGenerator()` 用 Proxy 代理
`CreativeModeTab$DisplayItemsGenerator`（已核实方法签名
`accept(ItemDisplayParameters, Output)`）。

**顺带改进**：`addBlockItem` 改为在 **Output 接口本身**取方法
（而非实现类），并用 `Output.accept(ItemLike, TabVisibility)` 重载
—— 它内部自己 new ItemStack，省一层手工构造。
理由写在注释里：output 运行时类是游戏为 lambda 生成的合成类，
其可见性不受我们控制，接口上的签名才是稳定定义。

### 累计的方法级教训（本项目反射踩坑清单）
1. `getMethod` 只返回 public → protected 用 `getDeclaredMethod` + setAccessible
2. `getDeclaredField` **不查父类** → 必须沿superclass 链
3. 泛型形参（`Supplier<T>`/`Function<T,R>`/双参函数式接口）**不能用 lambda** → 用 Proxy
4. 字段**不可变 + final**（Guava Immutable*）→ 整体 `Field.set` 替换，别指望 add
5. **实例非 null ≠ 实例可用** → 就绪判据要选真正代表"能用了"的字段
6. **实例化完成 ≠ 构造完成** → 半成品 final 字段仍为 null
7. `catch (RuntimeException)`漏掉 `ReflectiveOperationException`（本项目 4 次）
8. **错误信息要自证**：把真实字段名+类型打进异常（describeFields）

**这 8 条应该在写反射代码前先看一眼** —— 我是每次踩一个才发现。

```
because "this.gui" is null
  at Minecraft.reloadResourcePacks(Minecraft.java:1079)
```
`reloadResourcePacks` 第一件事就是读 `this.gui.overlay()`，
而 `gui` 在构造器**第 634 行**才赋值 —— 晚于 `resourcePackRepository`（第 434 行）。
所以"repository 就绪"时 gui 还没建好。
**就绪判据应选"目标操作真正依赖的最后一个被赋值字段"**，
而不是"看起来最相关的那个"。

### 方法层面的改进：构造器按【类型】填充，不按【位置】猜
`newLocationInfo` / `newSelectionConfig` 改成：
遍历候选构造器，**按参数类型**逐个填（String→id、Component→literal、
Optional→empty、enum→首常量、boolean→false），填不满就换下一个构造器。
这样 record 增删字段不再需要改代码 —— 上一版两处都栽在"位置写死"上。

### 新增到反射清单（第9、10 条）
9. **静态 vs 实例**：接口里的 `register` 常是 `static`，须以 null 为接收者；
   参数个数不符的报错容易让人误以为是"参数类型不对"
10. **ResourceKey 工厂**：`ResourceKey.create(registry.key(), id)` ——
    `Registries.XXX` 是注册表的 key，不是 key 的工厂
11. **就绪判据要看目标操作真正依赖的字段**（gui vs repository），
    且要看**赋值顺序**（634行 vs 434行）

### 工具教训
编辑长文件时若替换范围没覆盖到旧代码尾部，会留下悬空的 throw + 括号失衡
（本次报 3 个"语句不应在方法外"）。**修编译错误前先跑括号平衡自检脚本**
（去掉注释与字符串后数 {} 与 ()），比等 3 分钟编译快得多。

## RegistryClassInitOrderTest 失败：把"有意豁免"变成显式声明

### 现象
CI：`ModDiscoveryIT` 已 PASS（上一轮的 merge 污染修好了），
只剩 `RegistryClassInitOrderTest > RegistrationPhase：注册表触碰点受保护 FAILED`
（`AssertionError at RegistryClassInitOrderTest.java:81`）。138 tests, 1 failed。

### 根因：**生产代码是对的，是测试规则太粗**
违规点：`RegistrationPhase.java:349`
`Object registry = Reflect.staticField(BUILTIN, "BLOCK");`（在 `drainUnregisteredBlocks()` 内）

这行**必须**保持裸触碰 —— 上一轮刚修过一个自己制造的 bug：
`drainUnregisteredBlocks()` 由 `closeRegistryWindow()` 在**窗口已关闭之后**调用，
而 `ensureRegistriesReadable()` 内部走 `openRegistryWindow()`，
遇到 `windowClosed=true` 会抛 "The registration window is already closed"。
**加保护必然炸，且会屏蔽掉该方法真正要报告的内容（未注册的方块）。**

原测试只认两种豁免：8 行窗口内有 `ensureRegistriesReadable()`、
或位于 `openRegistryWindow()` 内（60 行回溯）。
而这里的论证性注释有 **11 行**，正好卡在 8 行窗口外 —— 规则看不见"这是有意豁免"。

### 解法：第三种豁免 = 显式标记
- 标记格式：`// [registry-exempt: <理由>]`
- 放在触碰点所在 `try` 块内（从触碰点向上回溯，遇 `try {` 停止，上限 60 行）
- 报错文案会提示这个标记，让后来者知道存在这条出路
-生产代码已加标记（`// [registry-exempt: 窗口已关闭，无法开窗]`）

**设计要点**：标记的价值不在"让测试闭嘴"，而在**强制作者把理由写下来**。
没有理由的豁免过不了 review，标记本身就是理由的锚点。

### 假绿检测（这次抓到了自己两个 bug）
改完规则必须验"移除标记后能否重新报警"，结果连续暴露两个问题：

1. **标记会"诈尸"**：我最初实现用 `lines[i].contains(MARK)`，
   而我又在下方注释里写了「上面的 `[registry-exempt:]` 是...要求的」——
   这句**讨论标记的说明行本身含标记字面量**，删掉真声明后豁免仍生效 → 测试假绿。
   修法：只认**专门的声明行**（先判 `//` 或 `*` 开头，剥前缀再比 marker）。
2. **漏算一个空格**：`t.startsWith('//' + MARK)` 对 `'// [registry-exempt:'` 返回 False，
   因为 `//` 后有空格。修法：改成 `t.substring(2).strip().startsWith(MARK)`，
   顺带让 `//[registry-exempt`（无空格）也能命中，消除易碎性。

最终验证（用 Python 复现测试逻辑，未跑 Java）：
正向 4 文件全 PASS；负向1 移除标记 → 抓到349 行；负向2 无空格标记 → 仍抓到。

### 教训
**放宽测试规则时，"假绿检测"是必做项，不是可选。**
我这次的检测脚本本身也写错过两轮（先抓错了行、又用了 Python 不存在的
`trim()` 而非 `strip()`），说明验证脚本也要复核 —— 验证工具出错时
结论会完全反向。

规则收紧的通用手法：把「隐式约定」（注释在窗口内）变成「显式标记」，
并让标记只出现在**唯一形态**上，避免讨论它的文字反而激活它。
