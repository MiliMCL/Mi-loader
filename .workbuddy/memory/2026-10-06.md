# 2026-10-06

## 修复 mili-loader.bat 在 Windows cmd 下的解析崩溃

**现象**：用户在 `D:\mili-0.1.0-mc26.2 (1)\mili-0.1.0-mc26.2\bin` 执行 `mili-loader.bat` 报四条错：
```
'浠?Mojang' 不是内部或外部命令
'local' 不是内部或外部命令
批处理参数替换中的路径运算符的下列用法无效: %~fI"
命令语法不正确。
```

**根因（经 2×2 对照实验 + 二分定位确认）**：
1. 主因：文件是 **UTF-8 中文 + LF 行尾**。cmd.exe 在 OEM 代码页（zh-CN 为 GBK/936）下按 CRLF 切分命令，LF-only 文件退化为按字节猜边界，把单行劈成碎片 → `setlocal` 的 `set` 被吞只剩 `local`；`%%~fI` 首 `%` 丢失报 `%~fI"` 无效。
2. 附带坑：**REM 注释行内的字面 `%` 也会被 cmd 展开**并破坏解析（我自己第一版修复注释里写了 `"%~fI"` 就再次触发，二分定位到第 12 行才发现）。
3. 中文不是必要条件——纯 ASCII + LF 遇到 `%` 展开同样会崩。中文只是让错误信息更难看。

**修复**：
- `mili-loader/distribution/bin/mili-loader.bat` → 改为纯 ASCII（英文注释）+ CRLF，注释中不出现字面 `%`
- `D:/mili-0.1.0-mc26.2 (1)/.../bin/mili-loader.bat` → 同步上述干净版本
- 新增 `.gitattributes`：`.bat`/`.cmd` 强制 `eol=crlf`，防止 `core.autocrlf` 检出时打回 LF
- `mili-loader/build.gradle.kts` 新增 `launcherScriptCheck` 任务（挂到 `check`/`build`），校验三条：无 BOM、纯 ASCII、全 CRLF 无裸 LF、REM 行无 `%`

**验证**：chcp 936/65001/437 三种代码页下零报错，参数透传正常，含空格与括号的路径解析正确。全程用 echo stub 掉 java，未启动 JVM（遵守用户"不在本机跑 Java"约束）。

**遗留**：D 盘旧版曾硬编码 `--gameDir "E:\mili-0.1.0-mc26.2\game"`（指向不存在的旧路径）、伪造 `--accessToken`、`${clientid}` 未展开；同步后这些参数已移除，回到干净模板形态。

**工具坑**：Write 工具在 Windows 上写出的文本文件是 **LF 行尾**，写 .bat 必须用 Python 显式 `.replace('\n','\r\n')` + `.encode('ascii')` 写二进制。

## 修复启动崩溃：SharedConstants ClassNotFoundException + 零Mod 静默失效

**现象**：`[Mili] ClassLoader 拓扑:` 打印后立即
`IllegalStateException: Mod registration failed` →
`ClassNotFoundException: net.minecraft.SharedConstants`，
并伴随 `0 registration(s) were queued by mods in their initialize() methods`。

**根因 1：生产路径从未调用 `Reflect.useGameClassLoader(...)`**
`Reflect.gameClassLoader()` 回落到 `Reflect.class.getClassLoader()`（平台 AppClassLoader），
而 Minecraft 类只存在于 `MinecraftClassLoader` 的 URL 里 → 平台 CL 看不见 `net.minecraft.*`。
**为什么测试全绿**：`GameTestClassLoader.install()` 调了它，所以「有 MC 的测试」永远看不到这个缺陷 ——
测试与生产的唯一区别就是这一行。

**根因 2：Mod 目录与 gameDir 不是同一个目录**
分发包布局是 `<dist>/{bin,core,mods,game}`：Mod 在 `<dist>/mods`，Minecraft 在 `<dist>/game`。
启动脚本传 `game/` 作 gameDir（正确），但平台按 `gameDir.resolve("mods")` 找 Mod → 扫到不存在的 `game/mods/`。
`ModDiscovery` 不抛异常只返回空列表 → **静默失效**：游戏正常启动、Mod 内容全空白、日志无任何线索。

**修复**：
- `Reflect.java`：`ThreadLocal<ClassLoader> GAME_CL` → `static volatile`。ThreadLocal 在此不仅无益（静态字段本就按定义它的 CL 隔离），还会让 `minecraft-main` 线程看不到主线程设的值 → 游戏运行期反射全部回落。
- `MinecraftGameProvider.createGameClassLoader()`：创建 MC CL 后立刻 `Reflect.useGameClassLoader(gameCL)`，必须在任何 Mod 加载/注册排队之前。
- `LoaderConfig.at(gameDir, modsDir)` 重载 + `LoaderMain.parseArgs()` 拆平台参数与 MC 参数。
  关键：MC 用 joptsimple，遇到不认识的 `--xxx` 直接 `UnrecognizedOptionException` 拒绝启动，平台选项必须在转发前摘掉。
- `ModClassLoader` / `ModClassLoaderManager`：新增显式 `modsDir` 构造参数；旧签名保留委托（`gameDir.resolve("mods")`），避免破坏 ~30 处测试调用点。
- `LoaderMain.reportDiscovery()`：打印 `[Mili] Mod 目录: ... (JAR/ZIP=n, 识别=m)`，`n>0 && m==0` 时报警。
- 两个启动脚本补 `--mili-mods "%MODS_DIR%"`；README 补该参数与两条故障排查。

**新增回归测试**：
- `DistributionModsDirTest`（loader）：分发包平级布局能发现 Mod，且断言 ModClassLoader **真的把 JAR 挂进了 classpath**（只看「能发现」不够，挂了才等于游戏能加载）。
- `ReflectGameClassLoaderVisibilityTest`：另起线程断言 `gameClassLoader()` 可见 —— 直接锁死 ThreadLocal 那个坑。不依赖 Minecraft，用替身 CL 即可。

**遵守约束**：用户机器 8G 内存、禁止本机跑 Java 进程，本次只做静态核对，编译与测试交由 CI（`compileJava compileTestJava` + `test` + `distTar`，均已覆盖这两个模块）。
